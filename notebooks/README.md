## V5, Whisper Large V3 → Tiny

Файл для импорта в Kaggle: [wakeword_bot_kaggle_v5.ipynb](wakeword_bot_kaggle_v5.ipynb).
Выберите **GPU T4 ×2**, включите Internet и выполните Run All. Весь код встроен,
API-ключи и исходный ZIP с датасетом не нужны.

Цель — recall не ниже 90% и FPR не выше 0.5% двухсекундных негативных окон,
отдельно RU/EN и в целом. Это цель нового эксперимента, а не достигнутый результат.
Предыдущий полный запуск V4 дал recall 66.4% (RU 60%, EN 70%), общий FPR 0.63%,
русский FPR 2%. V5 не снижает порог по test для получения желаемого процента.

Учитель — **Whisper Large V3**, многоязычный encoder с 128 mel-каналами, без decoder.
Дообучаются два последних слоя и бинарная голова, максимум 18 эпох с early stopping.
Для учеников Tiny отдельно вычисляются 80 mel-каналов. Мягкие оценки учителя
кешируются только для train; исходные метки остаются в loss, противоречивые
подсказки игнорируются. Сам учитель видит только train/validation. Два ученика —
baseline и distillation — обучаются через DDP; validation выбирает один из них.
Сравнение оценивает целые рецепты: seed, число дообучаемых слоёв и distillation
различаются, поэтому это не отдельная причинная оценка вклада distillation.

Проверка validation (включая EMA) и поиск сложных примеров train делятся между
обеими GPU без повторов окон; FP16 включён и при проверке. Результаты собираются
в исходном порядке manifest. Тайм-аут DDP — 30 минут. Это исправляет падение
первого запуска V5 из `notebook46c95e642b(1).log`: одна GPU проверяла весь Large V3
в FP32, а вторая ждала больше стандартных 10 минут. Генерация 115 100 окон прошла,
но учитель остановился после первой эпохи и ученик не был обучен/экспортирован.

Данные используют Silero v4/v5.5, Piper, MMS, Kokoro, реальные негативные слова
Speech Commands и необязательные вручную проверенные записи `REAL_WAKE_MANIFEST`.
Увеличен русский бюджет; негативы train синтезируются в трёх темпах, доли 65/20/15%
для похожих слов/контекстных упоминаний/прочих фраз. Голосовые группы не пересекаются.
Голоса V4 test уже изучались, поэтому этот benchmark регрессионный. Для нового
слепого теста нужны новые люди и условия записи, реальные положительные обращения.

После экспорта матрицы ONNX сжимаются в INT8. Выбор INT8/FP32 происходит на
validation, с допустимой потерей recall максимум 1 процентный пункт. Порог каждой
версии фиксируется отдельно на calibration; test открывается после выбора.
INT8 оценивается по одному окну, как в рабочем детекторе: batch влияет на
динамические масштабы активаций. При ошибке квантизации публикуется FP32,
причина сохраняется в `compression_selection.json`.
`training_report.json` / `output_summary.json` содержат явный `quality_gate`.
Даже passed относится к наблюдаемым оценкам benchmark, без гарантии на реальных
микрофонах или статистического подтверждения нижней границы 90%.

Рабочие файлы находятся в **`/kaggle/temp/wakeword-bot-v5`**; вывод — в
**`/kaggle/working/wakeword-bot-v5`**. Output включает `wake-model.zip`, альтернативный
малый ZIP, график, конфигурацию и отчёты. В ZIP только ONNX, frontend, порог и пример
запуска. Датасет, исходные STT/TTS-веса, учитель, PyTorch-веса и checkpoints не
публикуются. После окончания сессии продолжить обучение с checkpoints нельзя.
Для временных файлов нужно около 40 GiB свободного места; точный размер модели
и время определяются запуском. Малый `SMOKE` всё равно скачивает Large V3.

Сборка и локальные проверки без запуска обучения:

```powershell

.runtime/voice/Scripts/python.exe scripts/validate_wakeword_notebook.py --static --notebook notebooks/wakeword_bot_kaggle_v5.ipynb
.runtime/voice/Scripts/python.exe tests/wakeword_v5_test.py
.runtime/voice/Scripts/python.exe tests/wakeword_distributed_test.py
```

Полное обучение исправленного V5 завершилось на двух T4: предоставленный лог
`notebook46c95e642b(3).log` подтверждает обучение учителя, обоих учеников и экспорт
примерно за 5 часов 35 минут. Выбран distilled Tiny, эпоха 54, FP32: test recall
66,59%, FPR 0,559%. INT8: recall 73,23%, FPR 0,851%. Обе версии не прошли цель
90% / 0,5%. Модель FP32 занимает 30 941 023 байта; ZIP — 28 002 786 байт.
Подробный разбор и границы проверок: [wakeword_v5_results.md](wakeword_v5_results.md).

Два CPU-процесса дополнительно проверяют общую validation, пустой shard и mining
без обучения. Локальные проверки синтаксиса, границ дистилляции, ZIP и ONNX
не заменяют измерение качества на отложенных голосах и реальных записях.

## Детектор обращения «бот» / bot: Kaggle, две GPU

Самодостаточный файл: [wakeword_bot_kaggle.ipynb](wakeword_bot_kaggle.ipynb).
Фактические локальные эксперименты и ограничения: [wakeword_experiments.md](wakeword_experiments.md).
Импортируйте его в Kaggle, выберите **GPU T4 ×2**, включите **Internet** и выполните
ячейки по порядку. Подключать внешний Dataset, репозиторий или API-ключи не нужно.
Весь код и тексты включены в ноутбук; аудио генерируется нейросетями внутри Kaggle.

V4 использует четыре локальных семейства TTS: **Silero v4/v5.5/v3_en, Piper,
MMS/VITS и Kokoro**. По умолчанию 66 наборов модель/голос объединены в 61 группу
голоса: версии Silero одного диктора всегда относятся к одному split. Русский
train теперь содержит два голоса Silero, три Piper и один MMS вместо двух
голосов одного синтезатора. В полном режиме получается около 80 800 окон:
66 400 синтетических, 12 000 реальных отрицательных слов Speech Commands,
2400 процедурных фонов. Количество фактически выбранных реальных файлов
фиксируется в отчёте. Для Speech Commands загружается архив около 2.4 GB;
`REAL_SPEECH_SOURCE='mini'` уменьшает загрузку, `REAL_SPEECH_WINDOWS=0` отключает её.

Silero/MMS в двух процессах используют соответствующие GPU. Piper/Kokoro
работают в CPU ONNX; ноутбук не обещает CUDA для этих двух адаптеров. Все
выбранные движки обязательны, тихой подмены одним Silero нет. Примеры
сохраняются как WAV и FP32 признаки с тем же frontend, что используется в ONNX.

Основной вариант — многоязычный акустический **Whisper Tiny encoder**,
сокращённый до окна 2 секунды, с бинарной головой и attention/max pooling.
Дообучаются два последних encoder-слоя с LR 1e-5 и голова с LR 7e-4.
Decoder отсутствует; модель выдаёт только вероятность wake word.
Encoder включается в ONNX, для CPU инференса нужны NumPy и ONNX Runtime.
Альтернативы `temporal_v2` (CNN с нуля), `speech_embedding_v3` (готовые
Google/openWakeWord признаки) и `legacy` доступны для сравнения по validation.
Размер модели V4 около 7.7 млн параметров; старый детектор был намного меньше.

Другие улучшения:
баланс классов, языков и TTS, независимый pitch shift, умеренный шум,
реверберация, полоса пропускания и quantization, hard-example mining только
на train, EMA, максимум 100 эпох и early stopping. Два разных seed обучаются
последовательно, каждый через DDP на двух GPU. Validation выбирает лучшую
эпоху, сырые/EMA веса и одну модель либо ансамбль. Calibration фиксирует порог
с ограничением FPR отдельно для русского/английского и всей выборки.
Test не участвует в выборе; заранее заданы дополнительные профили FPR
0.2%, 0.5%, 1%, 2%, основной по умолчанию — 0.5%.

Для добавления реальных обращений задайте `REAL_WAKE_MANIFEST` путём к JSONL:
`wav`, `label` (0/1), `language` (ru/en), `speaker`, `split`, `reviewed: true`.
Записи должны быть вручную проверены, mono PCM16 16 kHz и короче двух секунд.
Один человек остаётся в одной части; одинаковое аудио с противоречивой меткой
или split отклоняется. Несколько новых людей в test нужны для проверки
качества на микрофонах, а не только на синтетике.

`STANDALONE_ONLY=True` означает отдельное имя перед сигналом. Параметры,
включая слово, движки, эпохи и объём данных, находятся в первой ячейке.
`WORK_DIR` V4 — `/kaggle/working/wakeword-bot-v4`: данные прошлых версий не смешиваются.
Для смены слова обновите также созвучные негативы во встроенном коде.

В Output появится `wake-model.zip` с CPU ONNX, весами, frontend, порогом,
отчётом, тестовыми предсказаниями и аудитом отброшенных источников. WAV и
признаки лежат отдельно в `dataset/`; `INCLUDE_DATASET_IN_ZIP=True` упаковывает
их. Для resume ансамбля нужен весь `checkpoints/` с `member-0/` и `member-1/`,
каждый содержит latest.pt и RNG обеих rank. `SMOKE=True` проверяет маленький
конвейер и помечает веса как **SMOKE-ONLY**.

Результат V1 из полученного архива: recall 14.5%, русский recall 9.5% при
FPR 0.25% всех тестовых окон. Это исходная проблема, не результат V4.
Повторный benchmark aidar/en_20–23 уже известен по V1; полностью слепой
окончательный тест требует нового корпуса. Новые TTS/голоса и реальные
негативы расширяют проверку, но не заменяют реальные положительные
обращения пользователей и длительные разговоры/музыку. Метрики FPR/window
не равны ложным срабатываниям в час. Ноутбук не включает детектор в боте.

Сборка и проверки:

```powershell
.runtime/voice/Scripts/python.exe scripts/build_wakeword_notebook.py
.runtime/voice/Scripts/python.exe scripts/validate_wakeword_notebook.py --static
.runtime/voice/Scripts/python.exe tests/wakeword_test.py
.runtime/voice/Scripts/python.exe scripts/validate_wakeword_notebook.py
```

QA-пакеты можно изолировать в `.runtime/wake-validation`; окружение бота
их не требует. Полная проверка выполняет TTS, обучение и экспорт на локальной
GPU, затем backward/resume в двух CPU Gloo-процессах. Физические две GPU
проверяются в Kaggle. Исполненная QA-копия остаётся в `.runtime/`.
Для сопоставления фиксированных моделей на одинаковых WAV:

```powershell
.runtime/voice/Scripts/python.exe scripts/compare_wakeword_models.py --baseline MODEL_V1 --candidate MODEL_V2 --dataset DATASET --output comparison.json
```

Этот скрипт заново калибрует оба порога на одинаковом calibration, затем
сравнивает одинаковый test. Сопоставлять числа на разных датасетах как прирост
точности нельзя.

## Обучение LIA / Laya

Откройте [laya_training_colab_kaggle.ipynb](laya_training_colab_kaggle.ipynb) в **Google Colab** или **Kaggle Notebooks**. Он самодостаточен: загружать исходники бота и клонировать репозиторий не требуется. Выберите GPU, загрузите размеченные JSONL и запускайте ячейки по порядку. Для Kaggle включите Internet при установке пакетов и скачивании базовых весов.

Ноутбук обучает реальный контракт `action` из `scripts/voice_worker.py`, включая основной и сокращённый вопросы. Экспортированный checkpoint загружается через существующий `LAYA_MODEL_PATH`. В нём предусмотрены выбор лучшей эпохи по validation, отдельная calibration, независимый test, метрики по классам, проверка TypeScript-правил и повторная загрузка сохранённых весов.

Текущий бот определяет обращение и допустимость команды правилами `VoiceSession`. Режимы автоплея/повтора/голоса и очистка очереди также разбираются в TypeScript. Поиск песен и выбор первого результата YouTube выполняются без Laya. Поэтому ноутбук не обещает изменить эти решения заменой checkpoint. Дополнительные вопросы `should_respond`, `next_tool`, `intent` можно обучить на отдельном контекстном корпусе; они пока не подключены к исполнению в боте. Старый музыкальный контракт v3 описан отдельно и не используется как основной профиль обучения.

## Подготовка данных

1. Включите `VOICE_NLI_LOG=1` в `.env` и перезапустите бот. Собираются только команды после активации, не фоновые разговоры и не аудио.
2. Проверьте исходный текст каждой выбранной записи `.runtime/nli/commands-*.jsonl` и создайте `reviewed.jsonl` с `{ "event_id": "…", "intent": "pause" }`.
3. Экспортируйте в новый файл:

   ```powershell
   npm run export:nli -- reviewed.jsonl reviewed-nli.jsonl
   ```

4. Загрузите `reviewed-nli.jsonl` в ноутбук. Можно вместо экспорта загрузить исходные журналы и указать `REVIEWS_PATH`. Также поддерживается прямой формат `commands-reviewed.jsonl`, описанный в ноутбуке.

Предсказания и результат исполнения не являются правильными метками. Не размечайте сбой поиска или `no_op` как `unknown`, если сама просьба была ясной. Число громкости остаётся аргументом, который проверяет код. Отрицания, составные просьбы и запросы к чужим устройствам должны присутствовать среди негативов.

Варианты одной фразы, сеанса или синтетического шаблона объединяйте через `group_id`. Точные совпадения исходного и приведённого текста группируются автоматически. Без семей/сеансов в данных автоматический split защищает только от точных совпадений, не от всех смысловых утечек. Технический минимум — четыре независимые семьи на класс; этого недостаточно для вывода о качестве. Нужны все восемь классов runtime и отдельные разнообразные примеры `play` и режимов. Для planner нужен другой корпус с реальным контекстом сессии, которого нет в обычном журнале.

## Следующий запуск Action V4 с авторской синтетикой

## Предыдущий Kaggle V3 со встроенными данными

Предыдущий приватный файл: `.runtime/datasets/lia_kaggle_v3_embedded.ipynb`.
Action V3 завершила 10 эпох, но не прошла gates: test macro-F1 0.811/0.591 для primary/short,
pause recall 0.708/0.000. Следующий action-эксперимент описан в V4 выше; V3 сохраняется для истории.
Импортируйте его в Kaggle, включите GPU и Internet и запустите **Save Version → Save & Run All**.
Сохранённая версия удерживает Output; интерактивная среда не заменяет сохранённый результат.
Данные и код уже встроены, дополнительные файлы не нужны. Все 44 записи бота сохранены:
31 автоматически размеченная запись используется только в train, 13 остаются для ручной проверки.

V3 разделяет смысл просьбы и допустимость её исполнения. Распознаваемая команда в запрещённой сессии
больше не становится `unknown` для смыслового классификатора. Владелец, канал, фаза, имя и право ответа
проверяются правилами. Контекстные сценарии сохранены как проверки этих правил, а не обучение NLI.
Балансируются классы, типы негативов, семьи и уникальные тексты; обучаются голова и четыре последних
слоя encoder. Лучший checkpoint выбирает validation macro-F1; calibration и test отделены.
Предсказания моделей не используются как правильные метки. Реальная точность требует новых ручных проверок.

`controls-v3` соответствует текущим восьми классам worker; `semantic-v3` — отдельная модель шестнадцати
смысловых действий, требующая будущей интеграции. Её нельзя подставить в `LAYA_MODEL_PATH` вместо action.
Проверки качества не ослаблены. При провале сохраняется ZIP с явной пометкой CANDIDATE для анализа,
при успехе — ZIP, прошедший проверки синтетического корпуса. CANDIDATE/SMOKE-ONLY нельзя подключать к боту.

После каждой эпохи атомарно сохраняется состояние обучения в `resume/`: веса, optimizer, scheduler,
GradScaler и RNG. Для продолжения после удаления среды добавьте сохранённый Output в Input и задайте
`RESUME_FROM` папкой `lia-v3`, содержащей **resume/ и candidates/**. Параметры должны совпадать.
Последняя диагностическая ячейка восстанавливает отчёты с диска без живых переменных.

```powershell
.runtime/voice/Scripts/python.exe scripts/validate_lia_v3_full_inputs.py
```

Генератор использует приватный `lia-balanced-v2`; распознанная речь, ноутбук с логами и веса остаются
в игнорируемой `.runtime/`. Проверка выполняет короткое GPU-обучение обеих моделей, реальное восстановление
optimizer/GradScaler/RNG, экспорт диагностик и повторную загрузку весов. Она не подтверждает качество полного обучения.
Отдельная проверка всех входов проверяет полный корпус на обрезание текста, совпадение вариантов ответа
после токенизации и соответствие правильных меток контракту модели.

## Первоначальный ноутбук V1

Дальнейшие инструкции относятся к первоначальному ноутбуку и ручному корпусу.
Совместное обучение V1 на встроенной несбалансированной синтетике привело к провалу управляющих классов;
для следующего эксперимента используйте V3 выше.

Для подготовленного стартового корпуса `lia-starter-v1` включите `ALLOW_AUTOMATIC_LABELS=True`: тогда ноутбук принимает явно отмеченную синтетику и разметку логов по правилам, сохраняя их происхождение. Для загрузки дополнительных контекстных сценариев задайте `AUTO_LOAD_PLANNER=True`. В архиве с датасетом есть копия ноутбука с этими параметрами. Это отдельный режим: непроверенные обычные журналы и предсказания модели по-прежнему не становятся обучающими метками автоматически.

Корпуса runtime и planner разделяются совместно по семействам, исходному и приведённому тексту. Одинаковая фраза в разных задачах или контекстах попадает в одну часть. Метрики на синтетическом и автоматически размеченном test характеризуют только этот корпус; для оценки на реальных пользователях нужен отдельный проверенный человеком набор.

Начните с `TRAIN_ENCODER=False`, batch 2, accumulation 8. Ноутбук использует supervised cross entropy по вариантам, не генерацию текста и не upstream RLCD. Для полного дообучения encoder задайте `TRAIN_ENCODER=True`, сравнивая варианты только на validation. Второй GPU не используется автоматически.

Скачайте ZIP после последней ячейки. Проверьте метрики, ошибки и `training_report.json`, распакуйте checkpoint в `.runtime/voice/models/laya-muz-bot-controls-v1/`, задайте:

```dotenv
LAYA_MODEL_PATH=.runtime/voice/models/laya-muz-bot-controls-v1
```

Перезапустите бот. Регистрация slash-команд не нужна. Удаление `LAYA_MODEL_PATH` возвращает базовый checkpoint из подготовленного кэша. Архив с `SMOKE-ONLY` предназначен только для проверки кода, его нельзя подключать как обученную рабочую модель.

## Проверка и обновление ноутбука

Исходные тексты участников, веса и отчёты остаются в игнорируемой `.runtime/`. Ноутбук хранится без результатов искусственного обучения. Для проверки подготовки данных нужны только Python и Node.js:

```powershell
npm run build
python scripts/build_laya_notebook.py
python tests/laya_training_test.py
```

Генератор встраивает актуальные вопросы, Python-обработчик и чистые функции из скомпилированных `intents.ts`/`music.ts`. Тесты проверяют SHA-256 исходников, синтаксис всех ячеек, недопуск непроверенных меток, защиту от утечки и реальные правила обработки команд.

При подготовленном локальном voice runtime можно выполнить проверку обучения, экспорта и загрузки на искусственных данных:

```powershell
.runtime/voice/Scripts/python.exe scripts/validate_laya_notebook.py
```

Этот запуск использует локальный кэш базовых весов, не устанавливает пакеты, пропускает графики при отсутствии matplotlib и сохраняет результат в `.runtime/notebook-smoke/validation.json`. Он проверяет вычислительный путь, но не подтверждает качество на речи пользователей. Полный запуск на реальном корпусе нужно выполнить в Colab/Kaggle; установка пакетов, доступность GPU и отрисовка проверяются там в первых ячейках.

После изменения контракта бота или `laya_training.py` снова выполните build и генератор. Обновление Laya требует повторной проверки внутренних функций токенизации и сохранения; версия закреплена как `0.3.22`, совпадающая с runtime.
