# Проверка оптимизаций

Основной профиль: один голосовой канал, VPS с одним vCPU и 1 ГиБ RAM,
`VOICE_PROFILE=light`, `STT_PROVIDER=groq`, `VOICE_CPU_THREADS=1`,
готовые TTS-ответы. Тариф Groq и биллинг эти изменения не переключают.
При исчерпании квоты API не повторяет аудиозапись автоматически; музыка
и текстовые команды продолжают работать. Локальная Whisper не загружается
как резерв при сбое Groq.

## Поведение

- `/skip`, голосовые «следующий трек» и «стоп» выполняются без затухания
  и без предварительного озвучивания. Остальные ответы сохранены.
- Получение метаданных: максимум два процесса, из них один фоновый.
  Одинаковые запросы объединяются; каждый потребитель отменяется независимо.
- Дочерний Node для JavaScript YouTube ограничен 128 МиБ heap по умолчанию.
  `YT_DLP_NODE_HEAP_MB` меняет лимит (96–1024, 0 отключает); явный лимит
  в `NODE_OPTIONS` имеет приоритет. RSS включает также память вне heap.
- Autoplay проверяет до трёх новых песен, исключая историю до проверки видео.
  Подбор начинается за 60 секунд до конца, подготовка аудио — за 20 секунд.
  Весь подбор с резервными исходными треками ограничен 25 секундами.
- Подготовка учитывает скорость и начинается после появления воспроизведения.
  На паузе отменяется; при возобновлении таймер пересчитывается. Готовность
  означает наличие PCM, а не создание процесса.
- ONNX проверяет поддерживаемые имена из конфигурации модели, включая
  «бот»/`bot`. Иные имена и отсутствие детектора используют STT.
  Неудачный запуск необязательного ONNX не отключает облачную STT.
- Нормализация, кодирование Opus, громкость, TLS, приватность команд,
  права управления и пятиминутный таймер отключения сохранены.

## Диагностика

Задайте `BOT_PERF=1` и перезапустите бот. Каждые десять секунд выводится
агрегированный JSON `[Performance]`: медиана/p95, размер выборки, кеш,
совместные запросы, event loop, память, CPU и число процессов.
Хранится максимум 4096 последних значений каждой метрики.
Речь, расшифровки, поисковые запросы, ключи и адреса потоков в этот JSON
не включаются. Диагностика выключается через `BOT_PERF=0`.

`command.ack` измеряет ответ Discord, `metadata.wait/work` — ожидание/работу
процесса, `audio.first/start/transition` — первый PCM/начало/переход,
`speech.wait/recognize` — очередь/распознавание,
`voice.action` — обработку до выполнения действия. `voice.total` дополнительно
учитывает настроенное ожидание тишины 400/800 мс; это оценка времени после
конца фразы, не аппаратное измерение момента её окончания.

На Linux дерево определяется по `/proc`, включая дочерние JavaScript-процессы
yt-dlp. CPU — оценка по периодическим выборкам, короткие процессы между
выборками могут быть пропущены. На Windows учитываются Node и зарегистрированные
дочерние процессы; отсутствующие данные обозначаются `null`.

## Воспроизводимые проверки

Сначала `npm test`: строгая сборка, автономные проверки и завершение процессов.
Затем `npm run test:integration`, `npm run test:radio`, `npm run test:groq`.
Последний отправляет только комплектные синтетические фразы.

Для замеров нужны настроенные yt-dlp/FFmpeg, доступ к YouTube, радио и Groq.
Сценарий воспроизводит аудио без входа в Discord и не записывает участников.
Он проверяет холодный/повторный/одновременный поиск, STT при воспроизведении,
реальные переходы yt-dlp → FFmpeg → Opus и продолжительную совместную работу.
В часовой проверке после STT и классификации выполняется пауза тестового
плеера с немедленным возобновлением. Соединение Discord и TTS здесь не измеряются.
Длительность трека в сценарии переходов фиксируется на 15 секундах,
чтобы проверить подготовку без ожидания полного окончания песни.

```bash
npm run test:performance -- --rounds=30 --output=.runtime/performance/candidate.json --soak-seconds=3600
```

Для сравнения сохранить прежний `dist` как отдельную сборку с доступом
к тем же зависимостям. Один и тот же новый сценарий запускает обе версии:

```bash
node dist/integration/performance.js --implementation=/absolute/path/to/old/dist --rounds=30 --output=.runtime/performance/baseline.json
node dist/integration/performance.js --rounds=30 --output=.runtime/performance/candidate.json --soak-seconds=3600
node scripts/compare-performance.mjs .runtime/performance/baseline.json .runtime/performance/candidate.json
```

Проверки выполняются последовательно на одном VPS. Дефолт — 30 повторений;
быстрая проверка допускает `--rounds=1`, но не подтверждает p95.
Облачные вызовы разнесены на четыре секунды, автоматических повторов нет.
При 429 сохранить отчёт и повторить проверку позднее после восстановления квоты.

Цели: p95 подготовленного перехода ≤1 секунды; p95 поиска и STT минимум
на 20% ниже исходного. Сравнение возвращает ненулевой код при нехватке
выборки, недостигнутых целях, ошибках или незавершённой часовой проверке.
Улучшение не считается доказанным только по успешным функциональным тестам.

Синтетические ответы проверяют механику и часть точности. Проверку человеческой
речи выполнить отдельно через `VOICE_TEST_FIXTURES` / `npm run test:voice`
на одном согласованном наборе WAV до и после изменения. Отдельно проверить
в Discord права, паузу, громкость, публичный `/player` и качество звука.

Для сравнения одного набора без печати расшифровок и с интервалом четыре
секунды между запросами:

```bash
node dist/integration/voice-regression.js --fixtures=/path/to/fixtures.json --implementations=/path/to/old/dist,dist --output=.runtime/performance/voice-regression.json
```

Отчёт содержит SHA-256 списка примеров, индексы, правильность и время.
Запускать только на согласованных записях: аудио отправляется в Groq.

## Интерфейсы и внедрение

Методы `video`, `search`, `searchCandidates`, `playlist` принимают необязательный
`AbortSignal` либо `{ signal, priority: 'foreground' | 'background' }`.
`related(id, limit, { signal, priority, excludeIds })` принимает набор исключённых ID.
Существующие вызовы совместимы. Лимиты и TTL поиска/видео сохранены.

Использовать отдельный каталог проверки, не заменяя работающую службу
до получения результатов. Внедрять диагностику, управление запросами,
подготовку потоков и голосовые изменения отдельными проверяемыми этапами.
Сохранять исходную сборку и настройки для отката; при регрессии вернуть
сборку предыдущего этапа и перезапустить службу. Определения slash-команд
не изменены, `npm run deploy` не требуется.
